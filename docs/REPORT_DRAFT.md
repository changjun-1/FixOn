# FixOn 프로젝트 보고서 초안

> 교수님 지정 보고서 양식으로 옮겨 작성할 원고다. 최종 제출 PDF가 아니다. 팀명·학번·이름·기간·실제 회의 기록은 팀이 입력해야 한다.

## 1. 프로젝트명

FixOn — 시설 고장 신고 및 정비 처리 시스템

- 과목: [입력]
- 팀명·팀원·학번: [입력]
- 수행 기간·제출일: [입력]

## 2. 목적 및 필요성

대학 내 시설 고장을 구두나 개별 메시지로 전달하면 신고가 누락되고 처리 현황을 알기 어렵다. 시설·분류별로 신고를 저장하고 관리자 확인부터 담당자 배정과 정비 완료까지 연결해 관리하기 위해 개발했다.

## 3. 프로젝트 개요

일반 사용자는 로그인 후 시설 고장을 신고하고 본인 신고의 진행 상황과 처리 결과를 확인한다. 관리자는 시설과 고장 분류를 관리하고, 신고에 정비 작업을 생성해 담당자·기한·처리 결과를 기록한다.

## 4. 주요 기능

- 회원 가입·로그인·로그아웃, 사용자·관리자 역할 분리
- 신고 등록·조회·수정·삭제·검색·통계
- 시설 등록·수정·삭제·활성 관리·시설별 신고·정비 이력
- 고장 분류 관리·중복 코드 방지·활성 관리
- 정비 생성·담당자 배정·상태 변경·기한 초과·통계
- 완료 처리와 신고 해결 상태 동기화

## 5. 시스템 구성 및 기술

수업 예제의 Node.js·Express·Nunjucks·Sequelize·MySQL을 기본으로 구성했다. Express가 HTML 화면을 제공하고 브라우저 JavaScript가 JSON API를 호출한다. Sequelize 모델을 통해 실제 MySQL 테이블을 조회·변경한다. bcrypt로 비밀번호를 해시하고 express-session으로 로그인 상태를 유지한다.

ARCHITECTURE.md의 다이어그램을 보고서에 삽입한다. app.js는 앱 구성, server.js는 DB 연결과 서버 시작을 담당한다. 수업 예제 대비 업무 라우터·권한·검증·상태 전이·테스트를 추가했다.

## 6. API 라우터 구성

| 업무 라우터 | 파일 | API 수 |
|---|---|---:|
| 신고 | routes/report.js | 8 |
| 시설 | routes/facility.js | 7 |
| 고장 분류 | routes/category.js | 7 |
| 정비 작업 | routes/workOrder.js | 8 |

업무 라우터는 4개, 업무 API는 총 30개다. 회원 5개와 CSRF 보조 API 1개는 업무 집계에서 제외한다. 전체 명세는 API_SPEC.md를 참조한다.

## 7. API 설계 예시

POST /api/reports에 facilityId, categoryId, title, description을 전달한다. 서버는 로그인 세션에서 작성자를 확인하고 시설·분류의 존재와 활성 상태를 검사한 후 REPORTED 상태로 DB에 저장해 201을 반환한다. 다른 회원의 신고 수정은 403, 없는 신고 조회는 404다.

PATCH /api/work-orders/:id/status는 작업 상태를 변경한다. IN_PROGRESS에서 COMPLETED로 변경할 때 처리 결과를 검증하고, 트랜잭션으로 작업 완료와 신고 RESOLVED를 함께 저장한다. 허용되지 않는 전이는 409다.

## 8. 데이터베이스 구조

users, facilities, categories, reports, work_orders의 5개 테이블을 사용한다. 회원·시설·분류와 신고는 1:N 관계, 신고와 정비 작업은 1:0..1 관계다. work_orders.reportId UNIQUE로 신고당 중복 작업을 방지한다. 참조 중인 시설·분류와 작업 연결 신고의 삭제를 제한한다.

ERD.md의 관계도와 필드 표를 보고서에 삽입한다. 서비스 DB fixon과 테스트 DB fixon_test는 같은 MySQL 서버에서 분리한다.

## 9. 화면 구성 및 구현

- 로그인·가입: 입력 검증과 오류 안내
- 대시보드: 실제 신고 통계·최근 신고
- 신고: 목록 필터·등록 폼·상세·처리 결과
- 시설: 목록·등록·수정·관련 신고·정비 이력
- 분류: 목록·등록·수정·활성화·관련 신고
- 정비: 생성·배정·상태·처리 결과·기한 초과
- 회원: 관리자용 회원 목록

screenshots/의 실제 구현 화면을 필요한 위치에 삽입한다. CSS는 데스크톱·작은 화면에 대응하도록 구성했다.

## 10. 핵심 API 테스트 방법과 결과

Jest·Supertest로 실제 Express 앱에 HTTP 요청을 보내고 응답과 MySQL 데이터를 검사했다. 테스트 전용 DB를 초기화하고 기본 계정·시설·분류·신고를 준비해 테스트 간 의존성을 제거했다.

자동 테스트 5개 파일, 총 36개 통과·0개 실패. 업무 라우터별 테스트는 신고 10개·시설 6개·분류 7개·정비 9개이고 화면·회원 응답 검증 4개가 추가되었다. 상세 실행 환경·범위는 TEST_REPORT.md를 참조한다.

브라우저에서 관리자 작업 생성·배정·진행·완료, 신고 상태 동기화, 시설 등록, 일반 사용자 로그인·신고 등록도 확인했다.

## 11. 구현 중 문제와 해결

- 개발 PC에 MySQL Server가 없음: 시스템 서비스 설치 대신 작업 폴더의 공식 MySQL ZIP으로 검증 환경을 마련했다. 제출 프로젝트는 일반 MySQL 접속 환경 변수로 실행할 수 있다.
- 수업 app.js가 즉시 listen을 실행함: server.js로 시작 부분을 분리해 테스트에서 앱을 생성했다.
- 회원·신고·작업 권한이 다름: 세션 로그인과 관리자 미들웨어, 신고 작성자 검사를 분리했다.
- 신고와 작업 상태가 어긋날 수 있음: 트랜잭션과 행 잠금으로 함께 변경했다.
- 동일 신고의 중복 작업 가능성: 부모 행 잠금과 UNIQUE 제약을 적용하고 동시 요청 테스트로 검증했다.
- 테스트가 시연 데이터에 영향을 줄 수 있음: fixon_test를 분리하고 DB 이름 안전 검사를 추가했다.

## 12. 개선 가능성 및 결론

시설 신고·확인·정비 결과를 DB 관계와 API로 연결했고, 수업의 라우터·모델 구조를 유지하면서 입력 검증과 권한·상태 규칙을 추가했다. 향후 이미지 파일 업로드, 알림, 담당자 직접 처리, 운영용 세션 저장소를 확장할 수 있다. 현재 범위는 로컬 대학 과제 시연이다.

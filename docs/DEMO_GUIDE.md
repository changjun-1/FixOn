# FixOn 심사 시연 안내

## 시작 전

1. MySQL 실행과 `.env` DB 설정을 확인합니다. `.env`와 실제 앱 키는 제출하지 않습니다.
2. `npm ci`, 최초 환경에서 `npm run seed`, `npm start`를 실행합니다.
3. 기존 서버가 있다면 종료 후 재시작하여 새 코드·환경변수·이력 테이블을 반영합니다.
4. 소셜 로그인은 APP_URL과 콘솔 Redirect URI가 정확히 일치해야 합니다.
5. 소셜 로그인이 불가능한 환경에서는 시연용 일반 계정으로 업무 흐름을 보여줍니다.

## 약 5분 시연

1. 학생 로그인 → 본인 신고 목록을 확인합니다.
2. 새 신고를 등록하고 상세에서 접수 이력·작성자·시각을 보여줍니다.
3. 관리자 로그인 → 해당 신고에서 정비 작업을 생성합니다.
4. 정비 작업에서 담당자 배정 → 진행 중 → 처리 결과 입력 후 완료합니다.
5. 신고 상세에서 해결 완료 상태와 정비 결과, 처리 이력을 함께 보여줍니다.
6. 다른 일반 회원으로 해당 신고에 접근하면 403이 되는 것을 설명합니다.
7. 자동 테스트 결과와 트랜잭션 롤백 검증을 보여줍니다.

기존 신고에는 기능 도입 이전 이력이 없습니다. 시연에서는 새 신고를 만듭니다.
처리 이력은 시설별 정비 목록과 다르게 개별 신고의 변경 과정을 보여줍니다.

## 설명할 설계 선택

- Nunjucks와 API를 한 Express 서버에서 제공하고, app.js·passport/·클래스 모델·test/ 구조를 교수님 step5 코드에 맞췄습니다.
- 모델·라우터·미들웨어를 분리하고 복잡한 작업 상태 변경을 서비스로 뺐습니다.
- 작업과 신고의 상태, 처리 이력을 같은 트랜잭션에 넣었습니다.
- 부모 신고부터 잠그며, 중복 작업은 UNIQUE 제약으로도 방지합니다.
- 관리자 권한뿐 아니라 신고 작성자 검사를 서버에서 수행합니다.
- 정비 담당자는 실제 수행자 기록입니다. 상태·결과 입력 주체는 관리자입니다.
- 일반·카카오·Google 계정은 별개이며 이메일만으로 합치지 않습니다.

## 자주 받을 질문

**DB는 어디에 있나요?** `.env`가 지정한 MySQL 서버입니다. Supabase가 필요하지 않습니다.

**로그인 상태와 업무 데이터는 어떻게 다르나요?** 브라우저의 세션 쿠키로 서버 세션을 찾고,
그 안의 passport.user에 저장한 회원 ID로 users를 조회합니다. 신고·정비·이력은 MySQL에 유지됩니다.
로컬 기본 메모리 세션은 재시작 시 사라지고, SQL 세션은 선택적으로 사용할 수 있습니다.

**이력 저장이 실패하면요?** 업무 변경도 롤백합니다. 이를 실제 MySQL 테스트로 검증했습니다.

**과거 기록도 모두 보이나요?** 기능 도입 후 앱 API로 발생한 변경만 보입니다.
DB 직접 수정은 자동 추적하지 않으며 신고 삭제 시 해당 이력도 함께 삭제합니다.

**배포나 실제 소셜 로그인 검증은 했나요?** 앱 키·반환 주소 설정과 자동 인증 흐름 검증은
완료했지만, 실제 제공자 계정의 최종 동의·콜백 성공은 별도 확인 대상입니다.

## 제출 전 확인

- `npm test`: 전용 fixon_test DB만 초기화합니다. 실제 업무 데이터를 넣지 않습니다.
- `npm run check`: JavaScript 구문 검사입니다.
- 작은 화면에서 로그아웃·목록·폼을 확인합니다.
- README, API_SPEC, ERD, ARCHITECTURE, TEST_REPORT 내용을 최종 코드와 맞춥니다.
- 소셜 앱 키, `.env`, node_modules, DB 원본 파일을 제출 ZIP에서 제외합니다.
